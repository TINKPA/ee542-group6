1. Setting up Hadoop on AWS EC2

In this tutorial, you will set up a two-node Hadoop cluster on AWS EC2, run MapReduce jobs on the Gutenberg dataset, and then extend the setup to learn about Spark. You will then compare the performance of Hadoop and Spark implementations.

Go through the links below for a detailed understanding of Hadoop, containers, and the map-reduce architecture.

Step 1: Launch Two EC2 Instances

  1. Log into AWS and launch two Ubuntu 22.04 EC2 instances (t2.medium recommendedc7i-flex.large). E-15. t2 is a burstable family: once CPU credits are exhausted the instance is throttled. Sections 3 and 6 are entirely about execution time, so a throttled run silently corrupts the only numbers this lab produces. If you must use t2.medium, watch CPUCreditBalance and mark the throttled intervals on every plot.
  2. Configure security groups to allow SSH (port 22) and Hadoop ports (50070, 8088, etc.9870 for the NameNode UI, 8088 for the YARN ResourceManager, plus all traffic between the two instances). E-1. 50070 was the NameNode UI in Hadoop 2.x. In 3.3.6 dfs.namenode.http-address defaults to 0.0.0.0:9870; opening 50070 gets you a port nothing listens on. The internal RPC ports (9000, 8030–8033, 8040–8042, 9866, 9867, and the ephemeral shuffle ports) are too many to enumerate, so allow the whole security group to talk to itself instead.
  3. SSH into both instances.
  4. Give the master passwordless SSH to the worker: generate a key on the master and append its public half to ~/.ssh/authorized_keys on both nodes. E-17 ✓ The handout never mentions this, and nothing in Step 3 works without it: start-dfs.sh starts the remote DataNode by SSH-ing from the master to every host in workers.

Step 3: Configure Hadoop

Edit configuration files (core-site.xml, hdfs-site.xml, mapred-site.xml, yarn-site.xml) on the master node to enable distributed mode and add the slave node's hostname in workers file.

E-9. The handout names four files and gives the contents of none, which is the single largest gap in it: "enable distributed mode" is a dozen properties, several of which have defaults that do not work on a 2 vCPU / 4 GiB node. The files below are the ones in code/setup/conf/. They go on both nodes, not just the master. Hostnames rather than IPs, with master and worker1 added to /etc/hosts on both machines.
Where to look this up. These files were not copied from a template — they were written for this cluster and confirmed by starting it. Three sources, in the order they are useful (all checked 2026-09-21):
  • Which properties a distributed cluster needs — the only official page on the subject:
    ClusterSetup.html (and SingleCluster.html for pseudo-distributed first). It covers all four files and etc/hadoop/workers, but it gives a property list and a few examples, not a working file — and it cannot size memory for you.
  • What every property means and what it defaults to — the dictionary, not a template: core-default.xml · hdfs-default.xml · mapred-default.xml · yarn-default.xml. This is where the port in Step 1 comes from: hdfs-default.xml lists dfs.namenode.http-address as 0.0.0.0:9870. Use the r3.3.6 path, not the r2.10.1 one the handout links.
  • What is actually in effect — the running cluster, which outranks both pages when they disagree with it: hdfs getconf -confKey <name>, or the full merged configuration at http://master:9870/conf and http://master:8088/conf. This is the only way to tell "I set it" apart from "it took effect".
The memory properties below (yarn.nodemanager.resource.memory-mb, the three *.memory.mb, vmem-check-enabled) are sized for a 2 vCPU / 4 GiB node. Change the instance type and they have to change with it; no documentation page can pick them for you.

2. Hadoop MapReduce with Python

We will use the Gutenberg dataset (Project Gutenberg books). Upload text files to HDFS:

hdfs dfs -mkdir /gutenberg
hdfs dfs -put *.txt /gutenberg/
E-13. The handout never says which books or how many, yet corpus size decides the answer to every question in Section 6 — a few MB is small enough that Hadoop's fixed startup cost dominates. Pin the set and record it: code/corpus.sh fetches a fixed list of ids and writes a manifest, in a small tier (6 novels, ~4 MB) and a large tier (~1 GB).

Python Mapper (wordcount_mapper.py)

#!/usr/bin/env python3
import sys

for line in sys.stdin:
    for word in line.strip().split():
        print(f"{word}\t1")
Correct as printed.

Python Reducer (wordcount_reducer.py)

#!/usr/bin/env python3
import sys
from collections import defaultdict

counts = defaultdict(int)
for line in sys.stdin:
    word, val = line.strip().split('\t')
    counts[word] += int(val)

for word, count in counts.items():
    print(f"{word}\t{count}")
cur, total = None, 0
for line in sys.stdin:
    key, _, val = line.rstrip("\n").partition("\t")
    if not val:
        continue
    if key != cur:
        if cur is not None:
            print(f"{cur}\t{total}")
        cur, total = key, 0
    total += int(val)

if cur is not None:
    print(f"{cur}\t{total}")
E-11. Streaming guarantees that records with the same key arrive consecutively, so the reducer can fold as it goes. The printed version holds the entire vocabulary in a dict, which is fine for six books and is the first thing to fail on the large corpus. Same output, bounded memory.

Run the MapReduce jobs:

#> hadoop jar /usr/local/hadoop/share/hadoop/tools/lib/hadoop-streaming-*.jar -input /gutenberg -output /output_wordcount -mapper wordcount_mapper.py -reducer wordcount_reducer.py
hdfs dfs -rm -r -f /output_wordcount
hadoop jar /usr/local/hadoop/share/hadoop/tools/lib/hadoop-streaming-*.jar \
  -files wordcount_mapper.py,wordcount_reducer.py \
  -input /gutenberg -output /output_wordcount \
  -mapper wordcount_mapper.py -reducer wordcount_reducer.py
E-2 ✓ Without -files the scripts exist only on the machine you typed the command on. On one node that is invisible; on two nodes the control run gives Task Id : ... Status : FAILED and the worker's syslog reads Cannot run program "wordcount_mapper.py": error=2, No such file or directory. E-10. The -rm is not optional either: a job whose output directory already exists fails before it starts, and Section 3 asks you to re-run these jobs.

Min/Max Word Count Reducer (minmax_reducer.py)

#!/usr/bin/env python3
import sys

min_word, min_count = None, float('inf')
max_word, max_count = None, float('-inf')

for line in sys.stdin:
    word, val = line.strip().split('\t')
    count = int(val)
    if count < min_count:
        min_word, min_count = word, count
    if count > max_count:
        max_word, max_count = word, count

print(f"MIN\t{min_word}\t{min_count}")
print(f"MAX\t{max_word}\t{max_count}")

This reducer is fine. What it is run on is not. It needs a second job over the output of the wordcount job, with an identity mapper and exactly one reducer:

# minmax_mapper.py — pass the word counts through unchanged
#!/usr/bin/env python3
import sys

for line in sys.stdin:
    key, _, val = line.rstrip("\n").partition("\t")
    if key and val:
        print(f"{key}\t{val}")
hdfs dfs -rm -r -f /output_minmax
hadoop jar /usr/local/hadoop/share/hadoop/tools/lib/hadoop-streaming-*.jar \
  -files minmax_mapper.py,minmax_reducer.py \
  -input /output_wordcount -output /output_minmax \
  -mapper minmax_mapper.py -reducer minmax_reducer.py \
  -numReduceTasks 1
E-3 ✓ Run the handout's way — this reducer directly over /gutenberg — and every record reaching it is word\t1, so the extremes of a set of 1s are 1. The control run printed MIN #1661] 1 and MAX #1661] 1: both bounds equal, both the same arbitrary token. The corrected two-pass version prints MIN <a hapax> 1 and MAX the 36214. -numReduceTasks 1 matters because a global extremum computed by several reducers gives one contradictory answer per partition.

Now, create a new mapper (char_mapper.py) and a new reducer (char_reducer.py) that count characters instead of words. Discuss the output results in the video log.

Worth knowing before you write it: the tab is Streaming's key/value separator, so a mapper that emits a literal tab or space as the key produces records the reducer cannot parse or a human cannot see. Escape them (<TAB>, <SPACE>) and the output is both parseable and discussable — the space is the most frequent character in English text by a wide margin, which is itself the first thing to say in the video log.

Add the second node's hostname to the master's workers file and restart Hadoop services. Re-run the jobs and observe execution time improvements.

E-10. "Re-run the jobs" fails immediately unless the output directories go first. Expect no improvement at this scale, and report that honestly. E-6. The mv two lines above puts Spark in /opt/spark; the export says /usr/local/spark. E-7. Single quotes defer the expansion to login. E-8. The printed quotes are typographic (“ ”); pasted into a shell they are written literally and the variable is never set. echo 'spark.yarn.jars hdfs:///spark-jars/*' >> $SPARK_HOME/conf/spark-defaults.conf
E-16 ✓ Not in the handout at all, and it decides Section 6. Otherwise spark-submit uploads 322 MB of jars into the application's staging directory on every submission. Same job, two runs each: 13.3 s and 11.2 s with the jars preloaded, 42.6 s and 35.2 s without. Comparing Hadoop against Spark without this measures a file copy.

5. Spark with Python (PySpark)

Two changes apply to all three scripts. E-4: SparkContext("local", …) hardcodes the master, so Spark runs in a single JVM on the submitting machine and the second node never participates — which makes Section 6's "on one node / on two nodes" question unanswerable with the code as printed. Take the master from spark-submit instead. E-5: "/gutenberg/*.txt" carries no scheme; under a local master it resolves against the local filesystem, so Spark and Hadoop would be reading different bytes.

Word Count (spark_wordcount.py)

from pyspark import SparkContext

sc = SparkContext("local", "WordCount")
text = sc.textFile("/gutenberg/*.txt")
sc = SparkContext(appName="WordCount")
text = sc.textFile("hdfs://master:9000/gutenberg/*.txt")
counts = text.flatMap(lambda line: line.split()) \
             .map(lambda word: (word, 1)) \
             .reduceByKey(lambda a, b: a + b)
counts.saveAsTextFile("/output_spark_wordcount""hdfs://master:9000/output_spark_wordcount")

Character Frequency (spark_charcount.py)

from pyspark import SparkContext

sc = SparkContext("local", "CharCount")
text = sc.textFile("/gutenberg/*.txt")
sc = SparkContext(appName="CharCount")
text = sc.textFile("hdfs://master:9000/gutenberg/*.txt")
ESCAPE = {" ": "<SPACE>", "\t": "<TAB>"}
chars = text.flatMap(lambda line: list(line)[ESCAPE.get(c, c) for c in line]) \
            .map(lambda ch: (ch, 1)) \
            .reduceByKey(lambda a, b: a + b)
chars.saveAsTextFile("/output_spark_charcount""hdfs://master:9000/output_spark_charcount")
The escaping is not required here the way it is under Streaming, but matching the MapReduce version makes the two outputs diffable — which is how you check that the two implementations agree before you compare their speed.

Min/Max Word Count (spark_minmax.py)

from pyspark import SparkContext

sc = SparkContext("local", "MinMax")
text = sc.textFile("/gutenberg/*.txt")
sc = SparkContext(appName="MinMax")
text = sc.textFile("hdfs://master:9000/gutenberg/*.txt")
counts = text.flatMap(lambda line: line.split()) \
             .map(lambda word: (word, 1)) \
             .reduceByKey(lambda a, b: a + b) \
             .cache()

min_word = counts.min(key=lambda x: x[1])
max_word = counts.max(key=lambda x: x[1])

print("MIN:", min_word)
print("MAX:", max_word)
min() and max() are both actions. Without .cache() the second one recomputes the entire shuffle. With it, the measured scans were 2.00 s and then 0.19 s — one line of code, and the cleanest single piece of evidence for Section 6's third question.

Submit them — this is the line that decides whether the second node is used:

spark-submit --master yarn spark_wordcount.py        # both nodes
spark-submit --master 'local[*]' spark_wordcount.py  # what the handout's code does

6. Performance Comparison

Now, run both Hadoop and Spark implementations and compare execution times.

Questions for students:

  • Which framework executed faster on one node? On two nodes?
  • Which framework is easier to implement in Python?
  • How does Spark's in-memory processing affect performance compared to Hadoop?
Measure two clocks, not one. The wall clock of the submitting shell includes client JVM startup and the YARN submission round trip; the application's own elapsed time comes from the ResourceManager at http://master:8088/ws/v1/cluster/apps/<appId>. That endpoint serves MapReduce and Spark applications alike, which is what makes the two frameworks comparable rather than merely both timed. In one measured pair: 16.3 s at the shell, 12.8 s for the application — the 3.5 s difference is overhead that belongs to neither framework's processing. At the handout's data scale most of the total is fixed overhead, so a single total lets you "confirm" the expected answer without evidence. Report both clocks so the overhead stays visible, and measure two corpus sizes — a few MB as the handout implies, and ~1 GB — because whether a second node helps is a question about size, and one size cannot answer it. Three repetitions per cell, since a difference smaller than the spread is not a result.

The rest goes in prose, not in a table.
  • Testbed — one paragraph: two c7i-flex.large, Hadoop 3.3.6, Spark 3.5.1, JDK 11, replication 2, both corpora (N books / M bytes each) from corpus.sh's manifest.
  • Q2, easier in Python — one sentence with counts: MapReduce minmax needs two programs and a second job over the first job's output with -numReduceTasks 1; Spark needs one script and two lines. Mention Spark's own traps (the master argument, the URI scheme) or the comparison is rigged.
  • Q3, in-memory processing — one measured pair: the first action on the cached RDD took 2.00 s and the second 0.19 s, same data, same job. Say also what that number is not: the whole Hadoop/Spark gap includes JVM reuse and the absence of an intermediate write to HDFS, not just memory.
  • Overhead — one sentence: of a 16.3 s wordcount, 12.8 s was the application and 3.5 s was client startup and submission. Enough to stop a reader from reading the totals as pure processing time.
Three runs per cell, reported as mean ± spread; a gap smaller than the spread is unresolved, not a win. Warm the cache first — the first run of any configuration is slower than every run after it.
