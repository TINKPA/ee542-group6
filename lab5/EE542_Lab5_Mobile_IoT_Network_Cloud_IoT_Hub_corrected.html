2. Set up Thingsboard Community Edition on Amazon Web Services

Configure and launch an Ubuntu Linux EC2 instance. A free-tier instance does work, but it is awfully slow to set up and run. So, you may want to use a larger instance with a modest fee. Make sure to configure your security group to allow all IPv4 traffic from anywhere (0.0.0.0/0). Open only tcp 22 (SSH), tcp 8080 (ThingsBoard UI), tcp 1883 (MQTT) and udp 5683 (CoAP) to 0.0.0.0/0. Moreover, make sure to create and download your security key. The downloaded file will have a name ending in ".pem" or ".ppk".

E-3 ✓ Those four ports are every port this lab uses. What "all traffic from anywhere" adds beyond them, from ss -ltnup on a running node (ThingsBoard 4.3.1.5 on Ubuntu 24.04, built by code/aws/tb_install.sh, 2026-09-22): tcp 7070 (edge RPC) and udp 5685–5688 (LwM2M and the other CoAP endpoints). PostgreSQL is not among them. It binds 127.0.0.1:5432, so no security group can expose it. Those extra listeners sit on a host whose ThingsBoard still has the published demo credentials from Step 5. The report should say which ports you opened and why. That is the one security decision this lab asks you to make.

Size the instance for the install, not for steady state: 4 GiB RAM is the documented minimum and install.sh in Step 5 is the memory peak. On a 2 GiB instance the install is OOM-killed with no error in the log.

E-7 ✓ Observed on 2026-09-21. The fix used was c7i-flex.large plus 4 GiB of swap, with the ThingsBoard heap capped at -Xmx2G so PostgreSQL keeps room. The handout says only "free-tier is slow", which reads as a patience problem rather than a failure mode.

Then, use the "ssh" terminal program to remotely log into the EC2 node.
https://docs.aws.amazon.com/AWSEC2/latest/UserGuide/connect-linux-inst-ssh.html

Your username should be ubuntu, and if you are using a Linux or Mac terminal with OpenSSH, you should be able to log in by typing the following (if your key file name is "key.pem" and your public IP address is "52.87.235.210"):

ssh -i key.pem ubuntu@52.87.235.210

The key file must be mode 600 (chmod 600 key.pem) or OpenSSH refuses it. E-9. A freshly downloaded .pem is world-readable and SSH fails with "UNPROTECTED PRIVATE KEY FILE", which does not mention permissions in its first line.

"Download and install an App named Owntracks from the Apple or Google App Store. On the App, go to Preferences. If everything was entered correctly, your phone should be sending several pieces of information to ThingsboardIO every 1 second."

E-4. This is the whole of §4 in the handout. Between "go to Preferences" and "everything was entered correctly" there is nothing: no field names, no values, no permissions, no mention that iOS will refuse the connection outright. Every step below had to be reconstructed. This is the single highest-severity erratum in the assignment, because it is the step that connects the phone to the hub, the point of the lab.

Step 0. Grant the location permission first

Set this before opening OwnTracks, in Apple's Settings app, not in OwnTracks:

  1. Open the iOS Settings app (the grey gear on the home screen, not OwnTracks' own settings).
  2. Scroll to the alphabetical list of apps at the bottom and tap OwnTracks.
  3. Tap Location.
  4. Choose Always. Not "While Using the App", not "Ask Next Time".
  5. On the same screen leave Precise Location on.
  6. Go back one screen and confirm Motion & Fitness is on. This is what feeds the step counter and the motionactivities field.

Why this is step 0. With "While Using the App", iOS delivers locations only while OwnTracks is on screen. The app still looks healthy, still publishes when you press the publish button, and still reports Move mode, so nothing tells you anything is wrong. Measured: with WhenInUse, 15 consecutive payloads showed an identical lat/lon/vel; after switching to Always the track moved normally.

Verify it rather than trusting the toggle. iOS sometimes grants a temporary "Allow Once" instead. Appendix B's status command makes the phone report its own permission state; you want:

"locationManagerAuthorizationStatus": "kCLAuthorizationStatusAuthorizedAlways"

The URL row is the one that matters, and it is far down the screen, below Secret encryption key and well past Host. Host, Port, TLS, Proto and Websockets sit higher up and look like the obvious place for a server address, but they are MQTT-only and are ignored in HTTP mode.

E-5 ✓ Source: OwnTracksAppDelegate.m:1815 passes url_preference to connectHTTP:, whose signature takes url / auth / user / pass / device / httpHeaders and no host, port or tls; Connection.m:455 then does request.URL = [NSURL URLWithString:self.url]. The MQTT path sets self.url = nil first and uses host/port instead. Putting the address in Host leaves the URL empty, and the failure is reported as kCFErrorDomainCFNetwork Code=2 … kCFGetAddrInfoFailureKey=8. That is EAI_NONAME, which reads like a DNS outage but is really NSURL finding no host to resolve. Omitting http:// produces the identical error, because then the scheme is parsed as the hostname.

Step 3. If iOS blocks the connection: App Transport Security

On iOS the plain http:// URL from §3 will be refused by the operating system, before any packet leaves the phone. Status Info → Status shows:

error The resource could not be loaded because the App Transport
Security policy requires the use of a secure connection.
E-6 ✓ Base.lproj/OwnTracks-Info.plist sets NSAppTransportSecurity → NSAllowsArbitraryLoads = false with no exception dictionary at all. There is no NSAllowsLocalNetworking entry either, so a private-range LAN address is refused exactly like a public one. The handout's entire §2–§3 build a plaintext http://…:8080 endpoint that an iPhone cannot talk to.

Three ways out, in order of preference:

  1. Put TLS in front of ThingsBoard. A reverse proxy (nginx/Caddy) on the EC2 host with a real certificate, so the phone posts to https://…. This is what a real deployment does and is the honest answer for the report.
  2. Use an Android phone for the HTTP leg. Android has no equivalent blanket restriction. If the team has both, this is the cheapest path.
  3. Tunnel it. Any transport that terminates TLS with a certificate iOS already trusts works. What we used during data discovery: tailscale serve --bg --https=443 http://127.0.0.1:8080, which issues a real Let's Encrypt certificate for the machine's *.ts.net name. iOS accepted it with no profile to install.

A self-signed certificate is not a fourth option unless you also install and trust its CA profile on the phone; ATS rejects it the same way.

E-13. Source: LocationManager.h:30, typedef NS_ENUM(NSInteger, LocationMonitoring) { Quiet = -1, Manual, Significant, Move }. A phone left at the default monitoring 1 looks configured and reports occasionally, which is easy to mistake for a working Move-mode setup.

The handout's "every 1 second" is not achievable, and the rate the app does produce is not a constant — it depends on how fast the phone is moving. The two Expert Mode rows are an OR, so a report is emitted whenever either condition is met first:

cadence = min(locatorInterval, locatorDisplacement ÷ v) = min(60 s, 50 m ÷ v)

That predicts a flat 60 s while slow, and a rate that climbs with speed once 50 m takes less than a minute to cover. Both halves were measured, on one iPhone, with the settings in the table above unchanged between the two captures:

The four fast bands match the prediction band for band, and the median step holds at 50–56 m across all of them — that is locatorDisplacement firing, not the timer. The crossover is where 50 m takes 60 s, i.e. v ≈ 3 km/h, walking pace. This is why the earlier 33.5-minute walk produced a clean one-per-minute and nothing else: walking sits almost exactly on the crossover, so the interval won every time. A capture that only ever walked will report "60 s" as though it were a property of the app rather than a property of the walk.

Battery, both captures, unplugged (bs = 1) throughout: stationary 3.8 %/h, walking 11 %/h, and 6.9 %/h averaged over the 8.7-hour mixed day. The cost is the GPS radio while moving, not the POST — a ~400-byte payload over an already-associated link is not what moves the needle. A true 1 Hz report rate would flatten the battery within the lab session, which is also why the handout's own closing NOTE warns about drain.

Consequence for §6: code/rendezvous.py resamples onto a 30 s grid with a 180 s max-age, both chosen against the 60 s walking cadence. Driving data arrives 15–30× denser, which the grid handles fine but which multiplies the volume — 8.7 hours of one phone is already 1353 fixes.

E-14 ✓ iOS does not expose a fixed-rate location timer to apps; locatorInterval is a desired interval passed to CoreLocation, which delivers updates when it has them. Quoting "every 1 second" in the report as if it were the observed rate would be reporting a number nobody measured — but so would quoting a flat "60 s", which is only the walking case. Report the rule, min(60 s, 50 m ÷ v), and the band table that establishes it.

Step 6. ThingsBoard expects flat key/value: check what arrives

ThingsBoard's telemetry endpoint stores a flat JSON object as key/value pairs. OwnTracks posts its own _type: "location" schema. The keys the dashboard in §5 needs (lat and lon) happen to be top-level, which is why §5 works at all. Nested values (inregions, inrids, motionactivities are arrays) are stored too, but as strings carrying the JSON text: readable in a table or a marker label, not plottable and not aggregatable.

E-16 ✓ The handout says the phone sends "several pieces of information" without saying which survive as telemetry. Replaying the capture into ThingsBoard 4.3.1.5 kept all 23 keys the phone sent, arrays included: motionactivities reads back as the string "[\"walking\"]" and inregions as "[]". The distinction that matters is type, not survival. A string key will not go into a chart or an aggregation. Before building anything in §6, open Entities → Devices → your device → Latest Telemetry and read the actual key list. That is the ground truth for what the dashboard can use.

  1. Status Info → Parameters shows the URL you intended. If it is blank you filled in Host. Go back to Step 2.

  3. Force one publish from the Map tab, then check Latest Telemetry in ThingsBoard. A manual publish arrives as t: "u"; a timer-driven one as t: "t" (Appendix A).

A.4 _type: "waypoints"

waypoints is an array of waypoint objects (each with desc, lat, lon, rad in metres, rid, wtst), plus _creator. Ours was []. No regions had been defined, so the region-based fields inregions, inrids and trigger t: "c" can never fire until you create some.

A.5 Data hygiene before you build on any of this

  • De-duplicate. 1 of 29 captured payloads was a byte-identical repeat. Key on (tst, tid). Repeats inflate path length and dwell time.
  • Sort by tst, not arrival order. Queued messages arrive late; that is what created_at marks.
  • Treat absent as absent, not zero. ssid vanishes on cellular; t was missing from 2 payloads.
  • Check variation before designing around a field. A field that never changes is a constant, not a measurement (acc here).

Appendix B: Remote commands

In HTTP mode the phone only ever speaks first, so the server's response body to a POST is the sole channel back. Returning a JSON array of command objects makes the phone act on them; returning [] is the documented "nothing for you". All of these require cmd on (§4 Step 5).

setConfiguration is a per-key merge, not a replace. Settings.m:408 guards every one of its 35 keys with if (object), so omitted keys keep their values. The inner object must carry "_type": "configuration" or it is rejected at Settings.m:418. Example, tightening the reporting cadence without touching the URL:

[{"_type": "cmd",
  "action": "setConfiguration",
  "configuration": {"_type": "configuration",
                    "locatorDisplacement": 50,
                    "locatorInterval": 60}}]

Sending a command is not the same as it taking effect. Follow every setConfiguration with a dump and read the value back; follow a permission change with a status. Both of the §4 errata that cost the most time looked exactly like success from the server side.

Appendix C: why point the phone at a local sink first

Before the phone talks to ThingsBoard, point it at a trivial HTTP server that stores every payload verbatim. ThingsBoard shows you the keys it managed to parse; a raw sink shows you what the phone actually sent, headers included. That is where X-Limit-U and X-Limit-D live.

That is what assignments/lab5/code/owntracks_sink.py does: it appends each POST body to a JSONL file with receive time and headers, answers [], serves a live per-_type field census on GET /, and stages the Appendix B commands via GET /cmd/<action>. code/census.py then prints, per field, coverage, observed range, and whether it varies at all. That last column is the one that matters. Every measurement in Appendix A came from those two scripts.

Note that the same ATS restriction (§4 Step 3) applies to the sink, so it too needs to be reachable over HTTPS from the phone.
